# i18n

Compile-time catalogs, binary-search lookup, no `HashMap`. Languages are Cargo
features. See RFC 0009 for the design rationale.

## Dependency requirement

`t!` and `traductions!` expand to absolute `::i18n::…` paths. **Any crate that
invokes them must depend on `i18n` directly**, even if it already depends on
`egui_sc` — the `egui_sc::i18n` re-export only covers the runtime API
(`set_language`, `current_language`, `export_catalogs`, `Languages`).

```toml
[dependencies]
egui_sc = { git = "https://github.com/lalvesl/egui_shadcn" }
i18n    = { git = "https://github.com/lalvesl/egui_shadcn" }   # required for the macros
```

## Declaring translations

`traductions!` is a **function-like** macro, not an attribute — the DSL is not
valid Rust on its own, so an attribute macro cannot parse it.

```rust
i18n::traductions! {
    pub enum Calendar {
        January([En("January"), PtBr("Janeiro")]),
        Month([En("The month {month}"), PtBr("O mês {month}")]),
        Apples(plural(n) {
            one:   [En("{n} apple"),  PtBr("{n} maçã")],
            other: [En("{n} apples"), PtBr("{n} maçãs")],
        }),
    }
}
```

The macro re-emits the enum **without** the language slices, so `Calendar::January`
is a plain unit variant, and implements `Translate`. The app id is a `const u16`
from FNV-1a hashing the enum name with a fixed salt.

## Using translations

```rust
ui.label(t!(Calendar::January));
ui.label(t!(Calendar::Month, month = some_str));
ui.label(t!(Calendar::Apples, n = 5));       // `n` is the declared plural driver
```

Returns `Cow<'static, str>` — borrowed for plain strings, owned only when a
placeholder or plural must be formatted. Call `.as_ref()` where a `&str` is
wanted, `.into_owned()` for a `String`.

There is **no `count` keyword**. The plural driver is an ordinary named argument
declared as `plural(n) { … }` and passed as `n = 5`.

Arguments are addressed **positionally** in the catalog: `t!` sorts the names it
is given and emits values in that order, and the catalog sorted the same names
the same way. Placeholder names therefore never appear in the binary, and a
translation may reorder them freely (`"{days} dias do mês {month}"`).

## Languages

```rust
i18n::set_language(lang);
i18n::current_language();
i18n::Languages::ALL          // iterate every known language
lang.bcp47()                  // "en-US", "pt-BR", …
```

Features: `lang-en`, `lang-en-us`, `lang-pt`, `lang-pt-br`. A language is in the
binary only when its feature is on; anything missing falls back to the async
`Source`. Component crates re-export these as their own features, so enabling a
language on `egui_sc` propagates down.

## wasm

`linkme` has no wasm backend, so distributed-slice registration is compiled out
on `wasm32` and catalogs must ship as **assets you generate and serve yourself**.
Without them, every string renders blank on the web build.

The pattern: give your native binary a catalog-export mode, run it as a build
step before the wasm build, and serve the output next to your bundle.

```rust
// in your native main(), before starting eframe
for lang in i18n::Languages::ALL {
    let bytes = i18n::export_catalogs(lang);
    std::fs::write(dir.join(format!("{}.cat", lang.bcp47())), &bytes)?;
}
```

Build that exporter with **every** language feature on, and make sure the binary
statically reaches every `traductions!` enum you use — `linkme` only collects
catalogs that are actually linked in.

On wasm, register the async catalog source and prefetch the active language
during setup so the first paint already has strings.

## Tests

The active language is global mutable state. Any test asserting a specific
translation must serialize on a shared `Mutex`, or it races under the parallel
test runner.
